# Development and deployment

Wooly runs a Vite React SPA and API in one Cloudflare Worker. Production retains `wooly-db`; the v1.0.0 runtime migration changed neither its schema nor its data. Root `package.json` and `bun.lock` are the sole version and dependency sources.

## Local development

Requires Bun 1.4.0 and Node.js 22.12+. From the repository root, using the machine-approved package registry:

```bash
bun install --frozen-lockfile
bun run db:migrate
bun run dev
```

Open `http://127.0.0.1:7014`. The Cloudflare Vite plugin runs the Worker and local D1 together, with remote bindings disabled. Daily state lives in `.wrangler/state`. `db:migrate` explicitly uses `--local --env local`; `dev` selects `CLOUDFLARE_ENV=local`.

Local identity requires `ENVIRONMENT=local` or `test`, a configured `LOCAL_USER_EMAIL` and trusted-host validation. The committed local environment supplies `developer@example.test`; no OAuth or production credentials are needed. Loopback URLs are the default entrypoint. The optional `wooly.dev.hexly.ai` proxy also requires a loopback `cf-connecting-ip` at the Worker; the local-host guard alone does not configure a proxy.

Do not run a second daily server. Build artifacts are generated by `bun run build`; Vite produces client assets and the Worker bundle under `dist/`. `bun run types` regenerates `worker/worker-configuration.d.ts` from Wrangler bindings.

## Validation

```bash
bun run typecheck
bun run lint
bun run test:unit:coverage
bun run test:worker
bun run test:api
bunx playwright install chromium
bun run test:e2e:bdd
bun run deploy:check
```

`typecheck` covers app, Worker and test TypeScript. App and Worker coverage each require all four metrics >=95% in their configured scopes. `deploy:check` builds and runs a Wrangler dry run; it does not publish. Run it without a selected local/test `CLOUDFLARE_ENV` when checking production output. [AGENTS.md](../AGENTS.md) records coverage exclusions and the actual hook/CI contract.

Normal Git hooks require `gitleaks` and `osv-scanner`; missing binaries fail. They run even for documentation commits. OSV scans the unified root lockfile. Do not bypass hooks or lower thresholds to publish changes.

### Test resources

| Lane | Runtime and state | Guard and cleanup |
| --- | --- | --- |
| App unit | jsdom, inline fixtures and mocked dataset transport | No production HTTP or D1 |
| Worker unit | Node Vitest plus local Miniflare D1 fixtures | Fresh fixture instances, disposed after use |
| API / L2 | Actual bundled Worker in Miniflare, loopback ephemeral port, `wooly-api-*` temporary directory | `_test_marker` UUID checked at setup/close and around dataset resets; runtime is disposed and only its own directory removed |
| Browser / L3 | Vite Worker on port 27014, `wooly-browser-*` temporary directory, test D1 binding | Local configuration and marker checked before startup; server reuse disabled; process stopped and owned directory removed |

API tests simulate both local and production authentication settings in local Miniflare with synthetic JWTs and a test JWKS service. They never connect to production D1. Browser tests create household data through the UI and cover persistence, direct nested URLs and session recovery. Real identity-provider login and exhaustive visual comparison remain manual checks.

The harness marker schema is `_test_marker(id TEXT NOT NULL)` with a per-run UUID. Browser teardown does not recheck it, and not every fixture/reset path independently checks it; those safeguards remain planned in [AGENTS.md](../AGENTS.md). `WOOLY_TEST_STATE` is assigned by the browser harness to its owned temporary directory, not to daily or production storage. Never deploy local/test environments or remote test resources.

## Production configuration

[wrangler.jsonc](../wrangler.jsonc) is the source of truth:

| Setting | Production value / role |
| --- | --- |
| Worker / domain | `wooly-web` / `wooly.hexly.ai` |
| D1 | Existing `wooly-db`, binding `DB`; preserve its ID and contents |
| Static assets | `dist/client`, `ASSETS` binding, Worker runs before asset serving, SPA fallback |
| `ENVIRONMENT` | `production` |
| `CF_ACCESS_TEAM_DOMAIN` | `nocoo` |
| `CF_ACCESS_AUD` | `733fc16e1ebab2704e6d1a878403d805255f7e16f0b492bf3955cf053af354d9` |
| `LOCAL_USER_EMAIL` | Empty; no local identity in production |
| `ALLOW_RESET` | `false` |
| Alternate URLs | `workers.dev` and preview URLs disabled |

The existing Access application controls allowed identities. The Worker verifies JWT signature, issuer, audience, expiry and identity claims. Mutations require a matching Origin. There is no application OAuth secret or shared API key. See the [API and authentication contract](10-maintainer-notes.md#persistence-and-api).

`/api/live` is public through the existing Access health bypass. It reports the root package version and a real D1 connectivity result; all other documented app/private API entrypoints require Access.

## CI/CD

[CI](../.github/workflows/ci.yml) runs for main pushes, pull requests and manual dispatch. It invokes `nocoo/base-ci` at the immutable revision pinned in the workflow, covering types, lint, app/Worker coverage, real HTTP tests, Chromium journeys, build, dependency/secret scans and workflow lint.

A successful **main push** CI triggers [Release](../.github/workflows/release.yml), which uses the pinned `deploy-worker.yml` workflow and the GitHub `production` environment. Pull-request CI does not deploy. Documentation-only pushes follow the same pipeline and redeploy the existing application version; they do not create a version tag or GitHub release.

Configure `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in that environment. The token needs account Workers Scripts Write and Account Settings Read, plus zone Workers Routes Write and Zone Read. Routine deployment does not require DNS Write. Deployment currently pins Node.js 26.8.1, Bun 1.4.0 and Wrangler 4.135.0; workflow files remain authoritative for later updates.

The deployment script validates approved production bindings and auth settings, builds, publishes the Worker/assets tagged with the root version, and then CI runs `bun run verify:production`. Schema migrations are separate. A manual Release workflow dispatch requires a successful main-push `ci-run-id` for the current commit.

## Manual deployment and verification

For an authorized manual deployment, privately configure the same two Cloudflare credentials and run from the root with `CLOUDFLARE_ENV` and `WOOLY_TEST_STATE` unset:

```bash
bun run deploy
bun run verify:production
```

The verifier reads production without changing data. It checks `/api/live` for the expected version, `storage: d1` and `database.connected: true`, then requires anonymous `/`, `/api/data` and `/api/session` to redirect to `nocoo.cloudflareaccess.com`. It does not prove authenticated CRUD or identify the deployed Git commit; use exact-SHA workflow evidence and, when relevant, an authenticated browser check as well.

If health returns a redirect, inspect the existing Access health bypass. If Access rejects identity, check team/audience and policy before changing application data. Unknown `/api/*` paths must return JSON rather than the SPA shell. Worker logs are enabled by Wrangler observability.

## Database changes

Schema migrations are reviewed and applied manually before dependent code is deployed:

```bash
bun x wrangler d1 migrations list DB --remote
bun x wrangler d1 migrations apply DB --remote
```

These commands target production; applying changes requires authorization and a reviewed backup/recovery plan. Run with no local/test environment selected. Routine development uses `bun run db:migrate`, which is explicitly local. Do not delete, recreate or reset `wooly-db` when cleaning up the old deployment.

## Versioned releases

From clean, current `main`, with `gh` authenticated and GitHub production credentials configured, preview the intended bump:

```bash
bun run release -- patch --dry-run
```

For an authorized release:

```bash
bun run release -- patch
```

Choose `minor` or `major` when appropriate. The script updates the root version and changelog, syncs the lockfile, commits and pushes with normal hooks, waits for CI and deployment of that exact commit, verifies production, then creates the tag and GitHub release. It uses the current machine registry for installation. Do not rerun a bump after a partial failure without checking the existing commit, tag and workflow state.

The completed v1.0.0 migration, production evidence and retained infrastructure cleanup list are in [11-workers-migration.md](11-workers-migration.md). Cutover incidents are recorded in [Retrospective.md](../Retrospective.md).
